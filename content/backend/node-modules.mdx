## Why This Matters in Real Projects

Dependency drifts and configuration leaks represent critical vectors for security breaches. Writing clear modules and securing environment keys ensures that code stays modular and production credentials are never committed into git histories.

<SeniorNote>
Always load environment configurations on application boot. In ES Modules, import configurations first before executing module code. Never check in `.env` files into source control.
</SeniorNote>

---

## Concept Explanation

### Module Formats in Node.js

Node.js supports two main module formats:
- **CommonJS (CJS)**: Uses `require()` and `module.exports`. Loads modules synchronously. Used by default.
- **ES Modules (ESM)**: Uses `import` and `export`. Loads modules asynchronously. Enabled by setting `"type": "module"` in `package.json`.

### Environment Management
Configuration variables (like database credentials, port bindings, API secrets) are injected into the container scope as variables and accessed via `process.env.VARIABLE_NAME`.

## Real-Time Project Example

<RealTimeExample title={"Modules, NPM & Environment Variables Scenario"}>
When deploying backends onto AWS or Render, credentials must change between development, staging, and production. Loading these settings dynamically from process.env instead of hardcoding API hosts allows the same container to run securely in all environments.
</RealTimeExample>

## Code Example

Below is a configuration file matching senior standards:

```javascript
// config.js (ES Module syntax)
import dotenv from 'dotenv';
dotenv.config(); // Parse and load environment keys from .env into process.env

export const serverConfig = {
  port: parseInt(process.env.PORT, 10) || 5000,
  dbUrl: process.env.DATABASE_URL,
  apiSecret: process.env.API_SECRET
};

if (!serverConfig.dbUrl) {
  throw new Error('CRITICAL: DATABASE_URL variable is not defined.');
}
```

## Interview Tip

<InterviewTip question={"What is the purpose of package-lock.json?"}>
package-lock.json records the exact dependency version tree installed at the time of locking, including nested dependencies. This ensures that every developer machine, CI build, and production server runs the identical package code, preventing dependency updates from breaking production builds.
</InterviewTip>
