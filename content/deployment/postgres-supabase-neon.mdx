## Why This Matters in Real Projects

Running local database containers in production is risky due to backup and availability challenges. Deploying to hosted cloud databases (like Neon or Supabase) ensures automated backups and scaling.

<SeniorNote>
Use connection pooling endpoints (PgBouncer) when connecting serverless applications to PostgreSQL. This prevents database instances from exhausting connection limits during scaling spikes.
</SeniorNote>

## Concept Explanation

### Cloud Database Integrations

- **Managed DB**: Cloud database instances managing patches, storage scaling, and backups automatically.
- **Connection Pooling**: PgBouncer pooling instances that reuse active connection links to avoid connection limits.
- **SSL Connections**: Database connection encryption strings enforcing secure data transfers.

## Code Example

Below is a configuration file matching senior standards:

```javascript
// Database configuration string using PgBouncer pooling
import pg from 'pg';

const connectionString = process.env.DATABASE_URL; // e.g. postgresql://dev:...@neon.tech:5432/db?sslmode=require

const pool = new pg.Pool({
  connectionString,
  max: 20, // Max active connection links
  idleTimeoutMillis: 30000,
  connectionTimeoutMillis: 2000
});
```

## Interview Tip

<InterviewTip question={"Why do serverless backends require PgBouncer?"}>
Serverless functions scale dynamically by spinning up isolated instances. Because each instance creates its own database connection, traffic spikes can easily exhaust PostgreSQL connection limits. PgBouncer pools connections to share links.
</InterviewTip>
