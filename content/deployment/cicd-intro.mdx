## Why This Matters in Real Projects

Deploying applications manually is slow and error-prone. Setting up automated CI/CD pipelines ensures that tests and validation checks run automatically on every pull request, preventing regression bugs.

<SeniorNote>
Add status checks in GitHub Actions to block merging pull requests unless workflow tests pass successfully.
</SeniorNote>

---

## Concept Explanation

### CI/CD Pipeline Stages

- **Continuous Integration (CI)**: Automates linting, formatting, and unit-integration test suites on code commits.
- **Continuous Deployment (CD)**: Automatically deploys code to staging or production environments after tests pass.
- **Actions Workflows**: YAML files defined in `.github/workflows/` that schedule tasks on events like pushes or pulls.

## Code Example

Below is a configuration file matching senior standards:

```javascript
// Basic GitHub Actions workflow config (.github/workflows/test.yml)
name: Continuous Integration
on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4
        
      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 20
          
      - name: Install dependencies
        run: npm ci
        
      - name: Run tests
        run: npm test
```

## Interview Tip

<InterviewTip question={"What is the difference between Continuous Delivery and Continuous Deployment?"}>
Continuous Delivery compiles builds automatically but requires manual approval before deploying to production. Continuous Deployment automatically deploys builds to production without manual intervention after tests pass.
</InterviewTip>
